De 30 a 5 minutos por SR, como escenario de piloto

Hasta un 83 % de ahorro estimado en preparación, creación y primera actualización. Incluye login recurrente por consola, búsqueda de identificadores y logs disponibles. La skill supone un perfil autorizado ya configurado y fuentes accesibles. No es un benchmark comparativo ni incluye diagnóstico complejo, instalación inicial o espera de Oracle. Oracle Support SR para Codex y Claude Code

Plugin privado de piloto. Un único código de skill y helper Python, con manifiestos para ambos agentes. Creación, consulta, notas con formato, adjuntos y cierre de SRs de OCI mediante el SDK/CLI oficial. Es una herramienta propia, sin aval oficial de Oracle. No incluye credenciales, datos de clientes ni un servicio de monitoreo desplegado.

Instalar

Requisitos previos: acceso de lectura a este repositorio privado, Git autenticado, el cliente CLI elegido en PATH, Python 3.11 y SDK oci>=2.177.0,<3 en el Python que usará el helper. Para instalar dependencias dentro del entorno Python aprobado:

python -m pip install -r plugins/oracle-support-sr/skills/oracle-support-sr/requirements.txt

Después de descargar/descomprimir el repositorio, la instalación en ambos agentes se ejecuta con una línea:

python install.py --agent both

También acepta --agent codex, --agent claude y --dry-run. Usa los instaladores nativos y no modifica credenciales ni permisos OCI. La primera autenticación, la asignación de privilegios y la instalación de dependencias son pasos previos; no se resuelven con una única orden de plugin.

Alternativa nativa Codex:

codex plugin marketplace add Diegoecab/oracle-support-sr
codex plugin add oracle-support-sr@diego-oci-support

Alternativa nativa Claude Code:

claude plugin marketplace add Diegoecab/oracle-support-sr
claude plugin install oracle-support-sr@diego-oci-support --scope user

Abrí una sesión nueva después de instalar. En Codex, invocá la skill desde el plugin instalado o pedí usar oracle-support-sr. En Claude, el nombre de la skill instalada como plugin es /oracle-support-sr:oracle-support-sr; una copia standalone utiliza /oracle-support-sr. No hace falta un MCP para este piloto. El SDK debe estar en el Python que ejecute el helper: si usás un entorno virtual, iniciá el CLI desde ese entorno o indicá al asistente la ruta del intérprete aprobado.

Para el ciclo completo, elegí un caso real de consulta o una validación controlada que no duplique un incidente existente. Indicá producto, síntoma, recurso cuando corresponda e impacto. Autorizá explícitamente la creación y el cierre de ese SR de prueba; verificá producto/categoría en el portal y la consulta posterior. No cierres un incidente de producción para probar el plugin.

Alcance validado y tiempos

El piloto ejecutó creación, consulta, nota, lectura de novedades, cierre y GET final en 32,062 s de ejecución automática sobre un SR de consulta. No incluye investigación ni todo el razonamiento del asistente. La referencia comercial de 5 minutos frente a 30 en consola expresa hasta un 83 % de ahorro estimado, incluyendo preparación y primera actualización; todavía no es un benchmark completo comparable. El formulario de consola también puede precargar información: medir ese flujo real antes de validar el ahorro del cliente.

Se confirmó el producto OpenSearch, pero una subcategoría solicitada no coincidió con el portal. El mapeo fino sigue pendiente de Oracle; es un requisito a resolver antes de prometer enrutamiento automático completo o habilitar creación desatendida. Los casos de consulta no prueban la recolección automática de logs de un incidente real.

Operación y mantenimiento

El helper conserva borradores, respuestas y recibos de escritura en el evidence-dir elegido. Las escrituras necesitan --execute y coincidencia de tenancy. No reintenta automáticamente escrituras inciertas: conciliar antes de repetir. Los recibos locales no sustituyen un registro compartido en Functions. Cerrar no elimina el SR; no se identificó una operación pública de borrado.

Las notas nuevas preservan estructura mediante HTML escapado; se verificó su renderizado en My Oracle Support. El API no reescribe comentarios anteriores. Las claves y la configuración OCI permanecen fuera del repositorio. SDK/CLI y comportamiento del portal pueden evolucionar; revisar referencias y validar en el entorno del cliente.

Entorno y autenticación

  • Python 3.11 y SDK oficial OCI oci>=2.177.0,<3 en el intérprete que use el helper. Las pruebas locales pasaron con 2.177.0; el ciclo original en vivo se ejecutó con 2.152.0. El backend CLI es opcional y necesita además OCI CLI.
  • Codex o Claude Code con ejecución local de comandos, almacenamiento de evidencia y conectividad HTTPS hacia los endpoints OCI utilizados. Para instalar desde este repositorio privado, también acceso GitHub y Git autenticado.
  • Perfil OCI con tenancy, usuario, región y API signing key registrada. Configurar la home region real; resolver la clave regional para el cuerpo de creación cuando corresponda. Las credenciales se administran localmente y no están incluidas en el plugin.
  • Tenancy de pago elegible para soporte, identidad provisionada en My Oracle Cloud Support y privilegios en el grupo de soporte del caso. Configuración de soporte, requisitos de creación.
  • Revisar las restricciones documentadas: Support CLI no está soportado en Cloud Shell; algunas llamadas SDK/CLI/API requieren que la tenancy esté suscrita a Phoenix y que se informe correctamente la home region. Problemas conocidos. La instalación no cambia suscripciones ni políticas automáticamente.

Campos que no deben faltar en el caso

Recurso/OCID cuando aplique, región, compartment conocido, síntoma, ventana UTC, request IDs, resultados observados, impacto, diagnóstico relevante y pedido concreto a Oracle. Seleccionar producto/categoría desde la taxonomía vigente y comprobar el enrutamiento persistido. Para OpenSearch, SRDC1037 agrega componente/subcomponente y evidencia condicional; requiere acceso autenticado.

La descripción inicial se limita al contrato actual; el helper aplica 1500 caracteres. Las notas y adjuntos conservan el detalle ampliado. MEDIUM es el enum de severidad 3; LOW corresponde a orientación general. Elegir la severidad por impacto documentado. No se promete un SLA por el nombre del enum.

Datadog: que el pager llegue con el SR preparado

Estado: arquitectura propuesta, sin despliegue ni prueba integrada en Datadog. El plugin interactivo ya gestiona SRs; la automatización de alertas necesita un runtime adicional en OCI Functions. No requiere una VM dedicada ni un MCP.

El patrón está documentado

El blog oficial de Datadog sobre Workflow Automation, publicado el 19/10/2022 y actualizado el 05/06/2023, muestra automatización a partir de eventos. La guía oficial de inicio implementa monitor -> ticket Jira -> aviso Slack con el enlace del ticket. Adaptar ese patrón a un SR de Oracle mediante una acción HTTP es nuestra propuesta; el ejemplo oficial no implementa OCI Support.

Arquitectura recomendada

Monitor crítico de Datadog
    -> Workflow Automation / acción HTTP
    -> OCI API Gateway + Function authorizer
    -> Function receptora: validar y persistir el evento
    -> Function worker: enriquecer, deduplicar, crear y consultar el SR
    -> Resultado durable: número, enlace, request IDs y evidencia
    -> Workflow: leer el resultado y emitir el pager con el SR

La receptora invoca al worker con fn_invoke_type='detached' y conserva el estado en un registro compartido, por ejemplo Object Storage con creación/actualización condicional por ETag. El 202 confirma procesamiento, no la existencia del SR. Una Function de conciliación programada revisa operaciones estancadas. Object Storage no dispara automáticamente el worker en este diseño. Invocación de Functions, autorización en API Gateway.

Un piloto acotado puede empezar con una Function síncrona si el presupuesto de tiempo de la acción HTTP lo permite. Para un webhook genérico, Datadog documenta 15 s por llamada y reintentos: conviene confirmar recepción rápido y separar el trabajo. Webhooks: payloads, headers y límites.

Cuándo se emite el pager

PolíticaComportamientoResultado para guardia

El primer modo se aproxima al objetivo del cliente. No garantiza que Oracle siempre responda antes del pager. En una alerta que exige aviso inmediato, usar el segundo modo. Revisar las notificaciones originales del monitor para evitar dos pagers por el mismo evento; probar un camino de fallback. Confirmar que Workflow Automation esté disponible y contratado en el sitio Datadog del cliente.

Datos y reglas para crear el SR correctamente

Mantener un mapeo aprobado por monitor/servicio: organización/sitio Datadog, monitor ID, tenancy y región OCI, grupo de soporte, producto/categoría/subcategoría, OCID o referencia de inventario, equipo dueño, runbook y regla de severidad con impacto justificado. Verificar el enrutamiento en el portal antes de habilitar creación desatendida. El mapeo fino de OpenSearch sigue pendiente de Oracle.

El worker reúne ciclo/grupo del alerta, instante UTC, prioridad, enlace/query del monitor, servicio/entorno, logs recientes acotados, métricas, lifecycle del recurso, errores y request IDs. Cada dato conserva fuente y hora. Se necesitan permisos de lectura para esas fuentes; la autorización para crear SRs no basta.

P1 de Datadog no implica HIGHEST de Oracle. La criticidad, el impacto actual, el workaround y los compromisos de contacto provienen de un responsable o política aprobada. Si falta contexto esencial, guardar AWAITING_CONTEXT y avisar a guardia con el borrador. Un LLM puede resumir evidencia autorizada; no debe obedecer instrucciones dentro de logs ni inventar impacto o identificadores.

Confiabilidad operativa

  • Autenticar el webhook con headers aprobados y authorizer; el POST genérico de Datadog no firma automáticamente solicitudes OCI. Verificar el monitor, limitar el tamaño del cuerpo y validar el destino contra un mapeo permitido.
  • Dedupe por organización confiable + ALERT_ID + ALERT_CYCLE_KEY + grupo/scope. Una renotificación del mismo ciclo actualiza el mismo SR; definir además correlación de incidentes para evitar un SR por cada host del mismo corte.
  • Persistir el intento antes del alta y tomar un bloqueo/revisión atómica. Ante timeout, marcar UNCERTAIN y conciliar antes de reintentar CreateIncident. opc-request-id no es una clave de idempotencia. Los recibos locales de la skill no resuelven concurrencia entre Functions.
  • Usar resource principal para Vault, estado e invocación de Functions según sus políticas. Para Support Management, partir de un usuario de soporte dedicado y provisionado, con signing key en Vault. La creación de SRs con resource principal no fue validada en este piloto.
  • Filtrar datos sensibles y adjuntar solo evidencia pertinente. Una recuperación puede agregar una nota si la política lo permite; no cerrar automáticamente un SR de producción porque una métrica se recuperó.
  • Medir alert-to-SR y alert-to-page P50/P95, duplicados evitados, errores de autenticación, mapeos faltantes y operaciones inciertas. Alertar también sobre fallas de la automatización.

Prueba propuesta

Elegir un monitor no productivo y un caso de prueba autorizado. Validar un solo SR por ciclo, producto/categoría correctos, evidencia completa, pager con enlace y fallback si Oracle falla. Incluir renotify, recovery, timeout tras aceptación, 429/5xx y cold start. El ciclo interactivo de 32 segundos no es una medición de esta integración.

Readable SR correspondence

The observed My Oracle Support portal interpreted correspondence as HTML and collapsed bare newlines. comment and close now use --text-format readable by default. Write the source note as text with blank paragraphs, ## section titles and - bullets. The helper emits escaped <p>, <br>, <strong>, <ul> and <li> elements. It treats log content and embedded HTML as text, never as markup to execute. It does not implement general Markdown, tables or arbitrary rich HTML.

Suggested note:

Hi Support,

## Summary
- Current symptom and impact.
- What changed since the previous update.

## Evidence
Operation: GetResource
UTC: actual test time
Result: actual status and code
Request ID: exact correlation ID

## Requested action
Specific investigation or supported remediation requested from Oracle.

Preview without credentials or a network request:

python scripts/sr.py --profile PROFILE --evidence-dir ./evidence comment --key SR_KEY --text-file update.txt --expected-tenancy TENANCY_OCID

The draft JSON contains the actual HTML that would be sent. After the already-authorized submission, re-read the case and verify the expected note and its CUSTOMER author. HTML may be normalized by the portal, so compare visible text if the serialized strings differ. API retrieval proves acceptance and storage; claim visual rendering only after inspecting the portal. --text-format verbatim preserves the exact input for an explicitly chosen existing contract; it bypasses the escaping formatter.

Use the supported comment workflow and UpdateActivityItemDetails model. The limited HTML convention is based on the observed portal, not a separately documented rich-text schema. No public edit/delete-correspondence operation was found in the reviewed client. If a previous note needs a readable replacement, append a clearly labeled summary only when requested; preserve the original audit trail.
