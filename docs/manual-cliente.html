Tiempo estimado para gestionar un SR

La comparación de trabajo rutinario usa 30 minutos por consola y 5 minutos con la skill: un ahorro estimado del 83 %. Incluye autenticación recurrente, identificadores, logs disponibles, preparación y primera actualización. Supone un perfil y una clasificación ya configurados y fuentes accesibles. Falta medir un flujo completo comparable; no incluye investigación compleja ni espera de Oracle. La consola puede precargar parte del contexto.

En una prueba anterior a los controles de clasificación de 0.3.0, seis operaciones automáticas de creación, lectura, nota y cierre llevaron 32,062 segundos. Fue una consulta sin recurso afectado ni logs de un fallo. El mapeo fino de OpenSearch sigue pendiente y esa ruta no está habilitada para nuevas altas técnicas.

El recorrido por consola y con la skill

Primero: cómo se haría desde la consola

Estos son, a grandes rasgos, los pasos para abrir y mantener un SR desde OCI/My Oracle Support: autenticarse, seleccionar el producto, reunir el contexto del recurso, completar el formulario, enviar y volver al caso para consultar o agregar evidencia. Parte de la información puede venir precargada si se inicia desde la página del recurso.

01 · Completar el diálogo de creación

Elegir producto, tipo de problema, categoría/subcategoría e impacto; completar título y descripción. Las opciones dependen de la selección anterior. Product/Category del portal no se deben equiparar por nombre con campos arbitrarios del API.

02 · Reunir identificadores y contexto

Obtener recurso/OCID, tenancy, compartment, región y ventana del problema cuando correspondan. Revisar qué datos ya se precargaron y completar los faltantes.

03 · Recopilar la evidencia del servicio

Consultar la guía de diagnóstico, reunir request IDs, errores, logs y métricas relevantes y filtrar lo que se compartirá. Para OpenSearch, revisar SRDC1037. Como opción adicional, ADB-S puede aportar información mediante su MCP nativo o SQLcl MCP, si ya existe acceso autorizado.

04 · Crear y comprobar el SR

Enviar el formulario, conservar el número y revisar producto, categoría, severidad y evidencia persistidos. La selección esperada debe contrastarse con el caso creado.

05 · Consultar, actualizar y cerrar

Entrar al SR para leer respuestas, agregar diagnósticos y archivos y, cuando corresponda, solicitar el cierre. No se borra el historial.

Después: cómo se hace con la skill

El usuario expresa el problema y su impacto en lenguaje natural. El perfil, recurso y SR ya seleccionados se reutilizan. La skill reúne el contexto accesible y pregunta únicamente por datos relevantes que falten; no requiere dictar IDs de taxonomía, JSON ni una secuencia de comandos de prueba.

Crear

Abrí un SR por el error de restore de este cluster de OpenSearch.

La skill identifica el recurso, recupera diagnósticos disponibles, propone severidad según el impacto conocido y consulta el catálogo. Usa una receta de clasificación verificada. Si esa receta no está habilitada, deja un borrador y explica qué validación falta; no crea el caso en una clasificación aproximada. El ejemplo OpenSearch/Backup and Restore permanece en ese estado pendiente.

Consultar novedades

Qué novedades hay en el SR?

Recupera la actividad y resume cambios, pedidos de Oracle y acciones pendientes. Distingue una respuesta de soporte de una nota del cliente o un mensaje automático.

Actualizar o adjuntar evidencia

Agregá este diagnóstico al SR y adjuntá el detalle si hace falta.

Prepara una nota legible con títulos y listas, publica lo autorizado y verifica la lectura posterior. Los archivos se revisan antes de cargarlos. La recolección mediante un MCP de ADB es una opción adicional y se configura aparte.

Cerrar

Cerralo; ya quedó resuelto.

Selecciona el SR del contexto, registra el motivo y consulta otra vez para confirmar CLOSED. La verificación es parte del trabajo del asistente y no requiere que el usuario pida cada GET interno.

Qué verá la persona

Número y estado del SR, producto/categoría esperados y su nivel de comprobación, resumen de la acción, evidencia y próximos pasos. Los comandos y JSON quedan disponibles como detalle técnico. El ciclo de crear, consultar y cerrar se usa para validar el piloto; no es una instrucción que el usuario deba repetir completa en una situación real.

Descargar las mediciones y salidas seleccionadas

Producto, subproducto y control de enrutamiento

Qué permite la API y qué está comprobado

La API permite enviar clasificación estructurada durante CreateIncident. El modelo oficial CreateTechSupportItemDetails expone category, sub_category e issue_type. En JSON de red se usan category.categoryKey, subCategory.subCategoryKey e issueType.issueTypeKey, dentro de ticket.resourceList[].item, con type=tech. No hay campos superiores llamados product y subproduct en el contrato revisado, ni un parámetro público para fijar una cola interna de ingenieros.

El catálogo oficial se obtiene mediante ListIncidentResourceTypes con problemType=TAXONOMY. Mantiene la jerarquía service group -> service -> service category -> subcategory. Los nombres Product/Category del portal no representan necesariamente los mismos niveles con los mismos nombres.

{
  "region": "IAD",
  "item": {
    "type": "tech",
    "category": {"categoryKey": "CATEGORY_KEY_FROM_LIVE_TAXONOMY"},
    "subCategory": {"subCategoryKey": "SUBCATEGORY_KEY_FROM_LIVE_TAXONOMY"}
  }
}

El ejemplo muestra la forma del contrato, no una receta lista para ejecutar. La clave de región se resuelve con Identity ListRegions. El SDK usa el nombre habitual de región para su endpoint. El comando CLI create aplanado no expone todo resourceList; usar SDK para esta clasificación.

No convertir el HTTP 200 ni las claves repetidas en una afirmación de que la cola es correcta. GetIncident devolvió actividades, sin el detalle persistido de clasificación necesario para comprobarla. Oracle todavía debe aclarar el mapeo fino; no inventar contextualData ni issueTypeKey para compensarlo. Una asignación interna tampoco es un atributo inmutable que este API garantice.

Como ejemplo de descubrimiento, la consulta del 17/11/2026 devolvió para OpenSearch: Backup and Restore, Connectivity, Import and Export, Performance y Cluster Provision and Resize. Ese listado ilustra el catálogo disponible en esa consulta, no cinco recetas verificadas. La skill vuelve a consultar el catálogo en el entorno del cliente.

El mapeo que necesita la skill

Usar dos registros distintos:

  • Catálogo disponible: obtenerlo de la API con el perfil del cliente. Guardar nombres, claves, jerarquía y fecha. Sirve para descubrir opciones, no para certificar el destino.
  • Recetas verificadas del cliente: relacionar las claves exactas del payload con Product/Category realmente observados en un SR creado por ese contrato, tenancy/grupo, fuente de evidencia, fecha y vencimiento. Solo el estado VERIFIED habilita creación técnica. Las recetas no van embebidas con datos de una cuenta en el plugin distribuido.

La persona describe servicio/recurso, síntoma e impacto. El LLM obtiene los IDs desde el catálogo y busca una receta válida; no le pide que memorice claves. Los aliases humanos ayudan a buscar pero no habilitan un mapeo por similitud de texto. Si la selección es ambigua o el mapeo es desconocido, preparar el borrador y explicar el dato pendiente.

Qué aplica la versión 0.3.0

El helper requiere --routing-file para ejecutar create de tipo TECH. Comprueba coincidencia de tenancy/grupo, región y claves del request, igualdad de producto/categoría esperados y observados en la evidencia, vigencia de esa evidencia y pertenencia de la ruta a la taxonomía consultada en vivo. Un cambio de etiquetas o de jerarquía detiene el alta. No hay receta técnica preaprobada incluida en el paquete.

El archivo es una configuración local mantenida por el cliente, no un nuevo campo del API. La skill lo resuelve desde el contexto/configuración autorizada y lo pasa al helper. El usuario no tiene que escribirlo en cada pedido. No marcar VERIFIED automáticamente, falsificar una comprobación, ignorar un vencimiento ni cambiar a raw API/CLI para sortear el control.

La inicialización de recetas requiere evidencia externa comprobable del mismo contrato o una validación controlada aparte, autorizada para ese propósito. El helper entregado no incluye una opción para omitir el control en producción. Una selección correcta en un SR creado por consola no prueba por sí sola el payload equivalente de API.

El catálogo puede exportarse en formato simple para la skill:

python scripts/sr.py --profile MI_PERFIL --evidence-dir ./evidencia taxonomy --catalog-file ./configuracion/catalogo-productos.json

Un archivo de receta tiene schema_version=1, status=VERIFIED, tenancy_ocid, user_group_id, routes y expected_portal. Cada ruta conserva region_key, las claves y etiquetas de la jerarquía exportada y, cuando no aplica, subcategory_key/subcategory_label nulos. verification contiene source, observed_at_utc, valid_until_utc y observed_portal.product/category iguales a expected_portal. Las fechas requieren zona horaria. La evidencia debe existir y referirse al contrato usado; esta estructura no otorga validez a una declaración sin evidencia.

El modelo público admite issueTypeKey, pero el guard actual no lo considera verificado con la taxonomía revisada y bloquea una creación que lo incluya. Esta limitación se documenta para no simular cobertura de un nivel que aún no se ha comprobado.

Después de crear con una receta válida, el resultado diferencia receta comprobada de asignación del nuevo SR. Revisar Product/Category persistidos cuando exista una lectura soportada; si requiere portal, mantener la comprobación pendiente hasta verla. No crear duplicados, cambiar otra clasificación o cerrar un SR para ocultar una discrepancia. Este control reduce el riesgo conocido; no promete una cola interna inmutable ni elimina la necesidad de verificar cambios de comportamiento de Oracle.

Oracle Support SR para Codex y Claude Code

Plugin privado de piloto. Un único código de skill y helper Python, con manifiestos para ambos agentes. Creación, consulta, notas con formato, adjuntos y cierre de SRs de OCI mediante el SDK/CLI oficial. Es una herramienta propia, sin aval oficial de Oracle. No incluye credenciales, datos de clientes ni un servicio de monitoreo desplegado.

Instalar

Requisitos previos: acceso de lectura a este repositorio privado, Git autenticado, el cliente CLI elegido en PATH, Python 3.11 y SDK oci>=2.177.0,<3 en el Python que usará el helper. El plugin se instala con los comandos nativos de cada cliente.

Si el marketplace ya está registrado, instalar es una orden por agente.

Codex:

codex plugin add oracle-support-sr@diego-oci-support

Claude Code:

claude plugin install oracle-support-sr@diego-oci-support --scope user

La primera vez se registra el catálogo privado, una sola vez en cada cliente. Para Codex:

codex plugin marketplace add Diegoecab/oracle-support-sr

Para Claude:

claude plugin marketplace add Diegoecab/oracle-support-sr

En Claude Code 2.1.292 o posterior, el comando de shell también permite registrar e instalar juntos: claude plugin install oracle-support-sr --marketplace Diegoecab/oracle-support-sr --scope user. En una sesión, la documentación ofrece /plugin install oracle-support-sr --marketplace Diegoecab/oracle-support-sr desde 2.1.275. Estas variantes requieren esas versiones; los comandos separados de arriba fueron los comprobados en el piloto. Documentación oficial de instalación.

Instalar el plugin no configura la identidad OCI ni otorga permisos. El SDK puede instalarse dentro del entorno Python aprobado con python -m pip install "oci>=2.177.0,<3". No hace falta descargar el repositorio ni ejecutar un instalador Python para registrar el plugin.

Abrí una sesión nueva después de instalar. En Codex, invocá la skill desde el plugin instalado o pedí usar oracle-support-sr. En Claude, el nombre de la skill instalada como plugin es /oracle-support-sr:oracle-support-sr; una copia standalone utiliza /oracle-support-sr. No hace falta un MCP para este piloto. El SDK debe estar en el Python que ejecute el helper: si usás un entorno virtual, iniciá el CLI desde ese entorno o indicá al asistente la ruta del intérprete aprobado.

Datadog: que el pager llegue con el SR preparado

Estado: arquitectura propuesta, sin despliegue ni prueba integrada en Datadog. El plugin interactivo ya gestiona SRs; la automatización de alertas necesita un runtime adicional en OCI Functions. No requiere una VM dedicada ni un MCP.

El patrón está documentado

El blog oficial de Datadog sobre Workflow Automation, publicado el 19/10/2022 y actualizado el 05/06/2023, muestra automatización a partir de eventos. La guía oficial de inicio implementa monitor -> ticket Jira -> aviso Slack con el enlace del ticket. Adaptar ese patrón a un SR de Oracle mediante una acción HTTP es nuestra propuesta; el ejemplo oficial no implementa OCI Support.

Arquitectura recomendada

Monitor crítico de Datadog
    -> Workflow Automation / acción HTTP
    -> OCI API Gateway + Function authorizer
    -> Function receptora: validar y persistir el evento
    -> Function worker: enriquecer, deduplicar, crear y consultar el SR
    -> Resultado durable: número, enlace, request IDs y evidencia
    -> Workflow: leer el resultado y emitir el pager con el SR

La receptora invoca al worker con fn_invoke_type='detached' y conserva el estado en un registro compartido, por ejemplo Object Storage con creación/actualización condicional por ETag. El 202 confirma procesamiento, no la existencia del SR. Una Function de conciliación programada revisa operaciones estancadas. Object Storage no dispara automáticamente el worker en este diseño. Invocación de Functions, autorización en API Gateway.

Un piloto acotado puede empezar con una Function síncrona si el presupuesto de tiempo de la acción HTTP lo permite. Para un webhook genérico, Datadog documenta 15 s por llamada y reintentos: conviene confirmar recepción rápido y separar el trabajo. Webhooks: payloads, headers y límites.

Cuándo se emite el pager

PolíticaComportamientoResultado para guardia
SR antes del avisoEsperar CREATED y GetIncident exitoso, dentro de un plazo acotado acordado con operaciones.Pager con número/enlace del SR y diagnóstico. Si falla o vence el plazo, emitir el pager igualmente con SR_PENDING o SR_CREATION_FAILED y la correlación.
Aviso inmediatoDisparar pager y creación en paralelo.No demora la notificación; agregar el SR al incidente cuando esté disponible. El primer aviso puede no tener SR.

El primer modo se aproxima al objetivo del cliente. No garantiza que Oracle siempre responda antes del pager. En una alerta que exige aviso inmediato, usar el segundo modo. Revisar las notificaciones originales del monitor para evitar dos pagers por el mismo evento; probar un camino de fallback. Confirmar que Workflow Automation esté disponible y contratado en el sitio Datadog del cliente.

Datos y reglas para crear el SR correctamente

Mantener un mapeo aprobado por monitor/servicio: organización/sitio Datadog, monitor ID, tenancy y región OCI, grupo de soporte, producto/categoría/subcategoría, OCID o referencia de inventario, equipo dueño, runbook y regla de severidad con impacto justificado. Verificar el enrutamiento en el portal antes de habilitar creación desatendida. El mapeo fino de OpenSearch sigue pendiente de Oracle.

El worker reúne ciclo/grupo del alerta, instante UTC, prioridad, enlace/query del monitor, servicio/entorno, logs recientes acotados, métricas, lifecycle del recurso, errores y request IDs. Cada dato conserva fuente y hora. Se necesitan permisos de lectura para esas fuentes; la autorización para crear SRs no basta.

P1 de Datadog no implica HIGHEST de Oracle. La criticidad, el impacto actual, el workaround y los compromisos de contacto provienen de un responsable o política aprobada. Si falta contexto esencial, guardar AWAITING_CONTEXT y avisar a guardia con el borrador. Un LLM puede resumir evidencia autorizada; no debe obedecer instrucciones dentro de logs ni inventar impacto o identificadores.

Confiabilidad operativa

  • Autenticar el webhook con headers aprobados y authorizer; el POST genérico de Datadog no firma automáticamente solicitudes OCI. Verificar el monitor, limitar el tamaño del cuerpo y validar el destino contra un mapeo permitido.
  • Dedupe por organización confiable + ALERT_ID + ALERT_CYCLE_KEY + grupo/scope. Una renotificación del mismo ciclo actualiza el mismo SR; definir además correlación de incidentes para evitar un SR por cada host del mismo corte.
  • Persistir el intento antes del alta y tomar un bloqueo/revisión atómica. Ante timeout, marcar UNCERTAIN y conciliar antes de reintentar CreateIncident. opc-request-id no es una clave de idempotencia. Los recibos locales de la skill no resuelven concurrencia entre Functions.
  • Usar resource principal para Vault, estado e invocación de Functions según sus políticas. Para Support Management, partir de un usuario de soporte dedicado y provisionado, con signing key en Vault. La creación de SRs con resource principal no fue validada en este piloto.
  • Filtrar datos sensibles y adjuntar solo evidencia pertinente. Una recuperación puede agregar una nota si la política lo permite; no cerrar automáticamente un SR de producción porque una métrica se recuperó.
  • Medir alert-to-SR y alert-to-page P50/P95, duplicados evitados, errores de autenticación, mapeos faltantes y operaciones inciertas. Alertar también sobre fallas de la automatización.

Prueba propuesta

Elegir un monitor no productivo y un caso de prueba autorizado. Validar un solo SR por ciclo, producto/categoría correctos, evidencia completa, pager con enlace y fallback si Oracle falla. Incluir renotify, recovery, timeout tras aceptación, 429/5xx y cold start. El ciclo interactivo de 32 segundos no es una medición de esta integración.

Actualizaciones legibles en el SR

El portal de My Oracle Support consultado interpreta las notas como HTML y agrupa las líneas de texto sin formato. La skill convierte párrafos, títulos y listas en una nota legible. Escapa el contenido de logs y diagnósticos para conservarlo como texto.

Una actualización puede tener esta estructura:

Hi Support,

## Summary
- Current symptom and business impact.
- What changed since the previous update.

## Evidence
Operation: GetResource
UTC: actual test time
Result: actual status and code
Request ID: exact correlation ID

## Requested action
Specific investigation or supported remediation requested from Oracle.

El asistente separa los identificadores largos y resume los hallazgos. Los logs extensos se adjuntan cuando corresponde. Antes de enviar, se puede revisar el borrador local; después, la skill consulta el SR para comprobar que la nota quedó guardada. La aceptación del API y la presentación visual en el portal son comprobaciones distintas.

El formato predeterminado del helper es --text-format readable. Admite párrafos, títulos con ## y listas con - ; no es un conversor general de Markdown. La convención de HTML limitado se comprobó en el portal y no representa un esquema de texto enriquecido documentado por Oracle.

Las actualizaciones agregan correspondencia. No reescriben ni eliminan notas anteriores. Si hace falta aclarar una nota previa, se publica una nueva cuando el usuario lo solicita.

ADB: MCP como fuente opcional de evidencia

ADB: evidencia adicional mediante MCP

Como complemento, una ADB Serverless puede aportar diagnósticos a través de su MCP nativo administrado. El asistente usa las herramientas autorizadas que la base expone y prepara los resultados relevantes para agregarlos al SR. Su configuración es un tema aparte y no es requisito para gestionar SRs por API.

El MCP nativo tiene un endpoint por base y expone las herramientas permitidas; no implica acceso SQL irrestricto. SQLcl es una alternativa, no un requisito del MCP nativo. En ambos casos se necesita conectividad e identidad con acceso a la información requerida. Los permisos para manejar tickets no conceden permisos sobre datos de la base.

La skill de SRs puede reutilizar esa evidencia ya obtenida, revisarla y adjuntarla mediante Support Management. No habilita MCPs ni cambia grants para abrir un ticket. Si la base no es accesible, se documenta esa limitación y se utiliza la evidencia disponible del control plane y de los logs.
