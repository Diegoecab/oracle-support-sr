# Monitoring, historical review, and existing Oracle MCP servers

## Current capability and MCP selection

Checked 2026-11-17. This skill's helper performs explicit CLI/SDK operations. It has no running scheduler, durable notification worker, or continuous history analysis. Do not describe design documents or offline comparisons as an active monitor.

Oracle publishes [OCI Support MCP Server](https://github.com/oracle/mcp/tree/main/src/oci-support-mcp-server). At commit `cdea374d50c230c221fe4ea306fcd953b3977ef9`, version 2.0.4 registers five tools: `list_incidents`, `get_incident`, `create_incident`, `list_incident_resource_types`, and `validate_user`. It uses FastMCP and the OCI Python SDK, supports stdio with an API-key profile and HTTP with caller IAM/IDCS token exchange. The package manifest requires Python >=3.13; do not assume an older helper environment can run it. Pin and inspect the version before installation. The repository describes these as reference/PoC implementations, not production deployments.

The reviewed dedicated MCP does not register update or attachment-upload tools. More importantly for monitoring, its `Ticket.resource_list` remains present, but its `Item` model and mapping discard activity `comments`, `activity_author`, `time_created`, and `time_updated`. A successful `get_incident` therefore does not establish that the response contains full correspondence. Use this skill's raw SDK/CLI response for correspondence, monitoring, and historical analysis until the MCP preserves those fields and is operationally validated.

Oracle also publishes a [generic SDK MCP](https://github.com/oracle/mcp/tree/main/src/oci-cloud-mcp-server), with operation discovery and invocation. Inspect `oci.cims.IncidentClient` and its exact contract before considering that route for missing operations. Its advertised generic invocation is an alternative to evaluate, not a tested support integration here. Preserve the skill's account selection, write receipts, and reconciliation rules; a generic tool does not supply those guarantees automatically. Do not build a new MCP solely because a previous search missed the existing one.

## OCI monitoring design

OCI Functions can be invoked by OCI Events for documented event producers. No Support Management producer was found in the [published catalog](https://docs.oracle.com/en-us/iaas/Content/Events/Reference/eventsproducers.htm) on the check date. Treat a native SR-change event as unverified; do not invent an event type or assume Audit emits complete support correspondence.

Recommended cloud design: scheduled invocation -> Function -> Support API -> durable snapshot and pending-delivery record -> OCI Notifications. Call the SDK directly from the monitor; an MCP server or LLM is not required to detect changes. Use Events when a documented source event becomes available; polling remains the fallback and reconciliation path.

[Resource Scheduler invokes Functions](https://docs.oracle.com/en-us/iaas/Content/Functions/Tasks/functionsschedulingfunctions-about.htm) using detached invocation. Each schedule has a [minimum interval of one hour](https://docs.oracle.com/en-us/iaas/Content/resource-scheduler/tasks/create-manage.htm), including CRON expressions. The docs explicitly support staggered hourly schedules. Two offset schedules provide a nominal 30-minute cadence; extending the pattern to twelve offset schedules for five minutes is a design inference requiring quota, timing, and overlap validation. Alternatively use cron on an existing persistent runner. Do not claim a single `*/5` Resource Scheduler schedule works. Schedule acceptance does not prove the detached function completed.

Keep snapshots and pending notifications in durable storage such as Object Storage with ETag conditional writes or a transactional database. A Function's temporary filesystem or local SQLite file is not durable shared state. Use a per-SR lease/conditional write to prevent overlapping invocations from issuing duplicate logical events. Maintain a stable event ID and pending-delivery state before publishing, then record acknowledgement. Publishing and state updates span services; duplicates remain possible after an ambiguous result or crash. Do not promise exactly-once delivery.

Functions can use resource principals for approved OCI storage, Vault, Notifications, and metrics operations. Support authorization is a separate validation: user/group visibility and support registration still matter. Do not claim a resource principal can read all technical SRs solely because an SDK signer exists. For the first cloud pilot, validate the accepted support identity. A possible fallback is a registered support user's signing key stored in Vault and accessed by the Function's resource principal, with rotation and no keys in the image or logs. Do not copy a local key into cloud storage without authorization for that credential deployment.

[OCI Notifications](https://docs.oracle.com/en-us/iaas/Content/Notification/Concepts/notificationoverview.htm) supports direct publishing and email, Slack, HTTPS, PagerDuty, and Function subscription protocols. Start with a requested endpoint. A subscription must be confirmed where applicable. Delivery is at least once and retry duration is finite (two hours by default); publishing success is not proof that a person read an email. SMS subscriptions accept messages only from supported services (Announcements, Monitoring, and Connector Hub at the check date); do not promise direct custom-published poller messages will reach SMS.

### Native SR delivery versus monitor destinations

The [SR creation guide](https://docs.oracle.com/en-us/iaas/Content/GSG/support/create-incident.htm) documents confirmation and follow-up emails to the primary contact. The reviewed [CreateIncident](https://docs.oracle.com/en-us/iaas/tools/python/latest/api/cims/models/oci.cims.models.CreateIncident.html) and [Contact](https://docs.oracle.com/en-us/iaas/tools/python/latest/api/cims/models/oci.cims.models.Contact.html) contracts expose contacts, email, phone, and group information, not an OCI Notifications topic, callback URL, or Slack/PagerDuty target. A contact phone number alone is not proof that arbitrary SR updates are sent by SMS.

Do not turn this API observation into a claim that all Oracle support channels are email-only. Oracle's [September 2026 onboarding material, slide 137](https://speakerdeck.com/oracle4engineer/onboarding-session-part1-hazimetenooraclecloud?slide=137), documents email/SMS preferences under Account -> Preferences -> Personal Information -> Notifications. Actual options, severity scope, and user opt-in must be checked in the selected portal/account before promising SMS for a noncritical SR. No native SR webhook was established in this review. This is separate from the multiple supported destinations available after our monitor publishes a Notifications message.

## Detection and operational acceptance

- First successful read establishes a baseline without replaying historical correspondence as new alerts. Later reads compare state, severity, pending party, activities, and attachment references.
- Prefer stable activity IDs when populated. If absent, normalize visible HTML text and links, retain author/type/timestamp/attachment ID, and use a multiset of hashes independent of response order. Distinguish new or changed activity from a proven new engineer response; automated ORACLE-authored messages can occur.
- Classify customer versus Oracle origin when supported by data, preserve raw evidence, and label unknown or automated origin honestly. Reordered results, formatting-only changes, and the monitor's own notes should not cause repeated engineer-response alerts.
- Read calls may use bounded retries with jitter and timeouts. Auth failures, 403/404, throttling, empty/truncated results, and malformed payloads must not reset the baseline or imply closure. For multiple SRs, validate pagination and modern modified-since contract support; periodically reconcile the complete visible scope.
- Record successful last-check time separately from last-change time. Export monitor heartbeat, errors, API latency, pending deliveries, and last successful publish. Alert on missing successful checks independently of ordinary SR updates.
- Before production, exercise unchanged/reordered snapshots, new Oracle and customer notes, status changes, missing activity IDs, overlap, restart, API failures, notification failure, retry exhaustion, and recovery. Validate subscription receipt end to end and measure observed detection latency. Keep local simulation, live reads, and live delivery results separate.

## Historical analysis equivalent

The [AWS support-cases skill](https://github.com/aws/tools-for-devops-agent/tree/main/skills/support-cases) is an investigation workflow: the agent loads relevant skill instructions, retrieves open/resolved cases with `DescribeCases`, paginates communications with `DescribeCommunications` as needed, and compares service, errors, resources, symptoms, and dates. It ranks relevance and summarizes evidenced causes and fixes. That skill does not implement an always-running historical indexing service or vector database.

For Oracle, use the current helper's paginated `list`, then full `get` for candidate SRs visible to the selected support user. Compare the same contextual signals and cite the original SR activity when proposing a prior remedy. Verify availability and visibility of older cases; do not transplant AWS's 24-month API window to Oracle. Separate documented root cause, successful prior action, and the current hypothesis. Schedule this analysis only if recurring analysis is requested; deterministic notification detection can run independently.
